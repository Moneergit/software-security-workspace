# 1 Purpose and scope

The Private Dataset Workspace is a small Python application that demonstrates how security can fail when separately running services are combined. Users can create private numeric datasets, inspect their own records and request a CSV export. The final implementation rejects the four planted attacks investigated in this report. [1]

Ali and John are ordinary seeded users. Admin has the additional ability to inspect global dataset metadata, including owner and title. This privilege does not grant access to another user's numeric rows or CSV results.

The functional requirements are login, dataset creation and search, private record retrieval, CSV export and retrieval, and administrative metadata inspection. Export involves all three services. The principal security requirements are to authenticate every protected operation, enforce ownership at the resource boundary, bind delegated authority to a specific operation, reject malformed input, and reject unapproved dependency artifacts. The detailed requirements, assets, access matrix and STRIDE analysis are in docs/security_design.md.

A dataset contains a title of at most 80 characters and between one and 100 integers. Each integer must be between minus one million and one million. These deliberately narrow constraints bound legitimate work and remove arbitrary text cells from the CSV format. The application has no registration, email, payments, public hosting or availability target. The optional malicious-helper and supply-chain experiments were not attempted. A separate installed helper package is nevertheless included because that architecture requirement is mandatory.

The development sequence is preserved in Git rather than reconstructed as an informal narrative. Commit faf9582 records the lifecycle plan before feature code. Commit dcabff9 introduces the services and four deliberate weaknesses; tag vulnerable-lab identifies that milestone. Commit 716e188 fixes the security boundaries. Later commits contain build gates, documentation and verified results. These commits record AI-assisted generation during this session, not independent student development. The separate declaration describes that assistance and must be completed before submission.

# 2 Components and trust boundaries

The Application API, Resource Service and Processing Service run as three independent uvicorn processes and communicate through HTTP JSON interfaces. The launcher assigns separate ports and process environments. SQLite is storage owned by Resource, not a fourth application component. The test fixture starts new processes with a temporary database and verifies distinct process identifiers.

API receives the password, verifies a salted scrypt digest and issues a user session. It coordinates requests but never opens the dataset database. Resource owns the SQLite datasets and results tables and makes the final ownership decisions. Processor receives an export job, retrieves authorized numeric rows, calls the installed workspace-csv helper, and sends the generated CSV back to Resource. API can subsequently retrieve the result for its owner.

The helper is a separate Python package with its own pyproject.toml, source directory and distributable wheel. requirements.lock declares workspace-csv version 1.0.0 and installs it from vendor alongside the approved third-party dependencies. Processor imports that installed package; its implementation is not pasted into the service.

The key trust boundaries are client to API, API to each downstream service, Processor to Resource, and the dependency installation boundary. Fixed configured URLs prevent callers from selecting arbitrary network destinations. Requests have five-second timeouts, do not follow redirects and do not inherit proxy settings. Resource validates returned CSV against its own expected serialization, preventing an accepted processing job from silently storing altered numeric output.

Separate processes are not a complete sandbox. They share one operating-system account in this local prototype, so a fully compromised process could attempt filesystem access outside its intended role. Environment minimization removes Resource keys and database paths from Processor's configuration, but does not establish OS access control. Production needs separate identities, filesystem permissions and network controls before stronger isolation claims are justified.

# 3 Identity and delegated authority

Authentication uses established mechanisms rather than custom cryptography. Password verification uses Python's scrypt implementation with a random salt for every seeded account. A successful login returns a signed JWT created through PyJWT. The session names the user, has audience api, carries action session and expires after 15 minutes. API checks the token and resolves the role from its own account store, so a caller cannot choose an administrative role in request data [7].

API creates a fresh Resource grant for each downstream operation. The signed claims carry subject, issuer, receiving service, action, dataset identifier, issue time, expiry and a token identifier. Collection operations use resource zero. Resource requires these claims, validates the signature with a fixed algorithm allowlist and checks the requested action and identifier before consulting ownership. Grant validity is one minute.

Export adds a Processor grant for action process and the same dataset identifier. Processor relays the Resource export grant; it cannot issue that grant because it lacks the Resource signing key. Resource authorizes both GET jobs and PUT jobs independently. The result is stored under the authenticated subject, and result retrieval filters by that subject. This prevents a service from treating its participation in a workflow as permission to access every user's records.

Three independently generated HMAC keys separate user sessions, Resource grants and Processor grants. API and Resource share one trusted signing domain; API and Processor share another. A compromised Resource or API is therefore beyond the selected containment boundary. Grants are reusable until expiry, not one-use capabilities. Restart rotates the in-memory keys and invalidates sessions. Production would need persistent key management, revocation and preferably asymmetric service signatures to separate signing authority from verification.

# 4 Vulnerabilities and investigation

The catalog provides three planted weaknesses: SQL injection, missing authorization and improper input validation [2]. A fourth weakness arises specifically in the export composition. The same four security assertions were executed against the vulnerable milestone and the fixed implementation. The original run failed all four assertions, with actual responses saved in evidence/vulnerable-tests.txt and its JUnit file.

V1 is CWE-89 in Resource's search endpoint. The original implementation concatenated the authenticated subject and search string into SQL. Ali submitted the search string shown in the evidence table and received metadata belonging to both Ali and John. The fix binds the owner and search pattern as SQL parameters. The regression now checks that every returned row belongs to Ali, including when the search contains SQL metacharacters.

V2 is CWE-862 on ordinary dataset reads. The original route accepted a valid grant for the requested identifier and fetched the record without comparing its owner with the subject. Ali's request for dataset 2 returned John's values with HTTP 200. The fixed route calls owned before returning rows. It returns the same unavailable response for absent and foreign datasets, reducing direct existence disclosure. Admin is subject to the same row-ownership rule.

V3 is CWE-20. The original dataset schema declared a list of integers without enforcing the documented 100-row quota. A request containing 101 rows was accepted with HTTP 201 and persisted. This demonstrates a security-relevant quota bypass and a precondition for excess storage or processing work; it does not demonstrate an actual service outage. The fix applies a bounded strict schema at both API and Resource, including integer ranges and unknown-field rejection. A direct Resource test confirms that bypassing API does not bypass validation.

V4 is a confused-deputy failure in service composition. API legitimately starts an export, but the original Resource jobs route assumed that a service-mediated request was already authorized for its subject. Ali could export dataset 2 and receive a ready result generated from John's rows. Fixing V2 alone would leave this separate jobs route exploitable. The correction checks ownership at job read and again at job save, while keeping subject, operation, dataset and expiry bound to the delegated grant. Result retrieval and output validation add further checks.

The observed cross-user disclosures receive high qualitative priority because an ordinary authenticated user can trigger them directly. The quota bypass receives medium priority in this local synthetic setting. These are contextual judgments, not computed CVSS scores. This follows the course emphasis on attack conditions and violated assumptions and the supplied prioritization reading's emphasis on context [4, 6]. The final branch has no runtime switch that re-enables the flaws; the vulnerable tag preserves them for controlled review.

# 5 Design principles and lifecycle decisions

Least privilege appears in both the roles and service grants. Admin can inspect metadata but cannot read foreign rows. Processor has no Resource signing key or account store and receives authority for only the current dataset export. Its key cannot authenticate a Resource request. Tests exercise that attempted forgery and mismatched resource scopes. [3]

Complete mediation means that the resource owner checks every relevant entry point. Resource authorizes ordinary reads, delegated job reads, job saves and result retrieval separately. It does not rely solely on API checks or trust a request because it originates from another service. Independent tests call internal endpoints with correctly signed but inappropriate grants. This is the principal lesson from V4: a secure ordinary read route does not automatically make the composed export secure.

Fail-safe defaults appear in missing-credential rejection, expiry and audience validation, strict input schemas and downstream error handling. A timeout or rejected downstream request stops the operation instead of returning foreign data or silently retrying with broader privileges. The tests cover missing credentials, invalid signatures, absent claims, expired tokens, wrong actions and wrong audiences. Keeping the domain small is a supporting design choice: fixed numeric CSV output avoids arbitrary filenames, browser rendering and general-purpose command execution.

The initial plan covers requirements, implementation and build, testing, and release/deployment/operation. Its requirements gate identifies assets and authorities before implementation. The later STRIDE matrix connects spoofing to token checks, tampering to parameterized SQL and validation, disclosure to ownership, elevation to roles, and availability to bounded inputs and timeouts. Metadata denial logs support investigation, although durable audit completeness and tamper resistance remain operational work. This is a concrete application of the course's asset-to-threat-to-control-to-evidence chain [5].

The plan also determines gate decisions. The vulnerable milestone is retained as investigation evidence but fails release requirements. Confirmed authorization and validation violations must be fixed before the final candidate passes. During dependency analysis, the initially seeded pip version produced advisory findings. It was replaced with the approved newer version rather than added to an ignore list.

Python's managed runtime reduces common manual-memory errors discussed in the course, but does not determine which user owns a record. FastAPI and Pydantic enforce the declared request schema; PyJWT handles signatures and registered claim checks; SQLite supports parameter binding and transactions. Application code still defines ownership, role semantics and delegation. Deployment choices determine network exposure and process isolation.

# 6 Verification and continuous integration

The final local validation contains 40 passing tests. Functional tests cover create, list, read, export, result retrieval and metadata auditing. Security tests compare owners, roles and credentials through real HTTP calls. Four artifact tests verify accepted bytes and rejection of changed, missing or unexpected files. Fixtures create a temporary database and fresh services, so test success does not depend on previous demonstration state. Saved test output and JUnit XML identify the executed cases and outcomes.

The suite includes internal-boundary checks as well as public API checks. It supplies legitimate test grants with the wrong subject, action, audience or dataset, attempts a Resource credential signed using Processor's key, submits altered CSV output and calls internal routes without authentication. Issuer keys are available to the test fixture solely to construct these adversarial cases. They are not published application credentials.

scripts/ci.py performs artifact verification, installed-distribution verification, compilation, a helper wheel build, Ruff lint and formatting, Bandit, pip-audit, the test suite and a smoke demonstration. It records every stage's exit status in reports/gates.json. Any failure blocks the candidate. The final snapshot records zero for every stage. Ruff and Bandit report no remaining findings in their configured scope. Bandit examines application and helper code; test assertions and the process-launching development harness are outside that security scan.

Dependencies install offline from an exact wheel inventory using SHA-256 hashes. The consumer-controlled manifest rejects additional or missing artifacts and changed bytes. A separate check compares installed names and versions with the approved list and verifies that the helper source matches its approved wheel. Public dependency advisories block regardless of severity. The local helper has no public advisory entry, so its documented skip is covered by source inspection, static analysis and artifact checks. Unknown skipped public packages and advisory-service failures block.

The Jenkinsfile starts with a fresh checkout on a Python 3.12 Linux agent, installs approved artifacts and executes those same local gates. It publishes JUnit results and archives analysis output even after failure. A GitHub Multibranch Pipeline with branch and pull-request discovery plus webhook configuration is required to schedule builds on both kinds of event [8]. This account-level configuration has not been performed here. The README explains it; actual hosted build URLs must be added after setup.

The evidence is bounded. Linux execution and fresh offline installation were verified. Windows x64 wheels and PowerShell commands are supplied, but a Windows run was unavailable. The tests do not prove freedom from all vulnerabilities, resistance to sustained load, or secure operation after complete host compromise. Dependency advisories are a dated observation and must be checked again when the project changes.

# 7 Release considerations and submission

The final implementation supports the required small workflow while correcting the demonstrated security failures. Its central result is that delegation preserves the user and requested dataset through every service boundary, and Resource independently enforces ownership before data leaves storage or a result is saved. A successful authenticated call is evidence of identity, not a universal access permission. This distinction explains both the original direct-read flaw and the separate export-composition flaw.

For production, the loopback-only deployment would need TLS and authenticated transport between services, separate operating-system identities or containers, restricted database and account-file permissions, and controlled outbound network access. Signing keys need protected storage, rotation and revocation procedures. HMAC verification keys also permit signing within their trust domain; asymmetric credentials would reduce that shared authority. Public demonstration passwords must be replaced, and login requires throttling and appropriate account protections.

Availability work must include incoming byte limits before JSON parsing, database growth quotas, concurrency and load testing, backup restoration and operational monitoring. Current row limits bound accepted datasets but do not prevent a client from sending an enormous HTTP body. Current logs provide metadata evidence for local investigation, not a complete durable audit system. Admin-visible titles must remain nonsensitive metadata. Updating dependencies also requires reviewing new artifacts and refreshing advisory evidence.

The supplied repository includes its full Git history, initial lifecycle plan, architecture and access matrix, helper package, Jenkinsfile, regression evidence and operating instructions.
