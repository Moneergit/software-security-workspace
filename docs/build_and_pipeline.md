# Build and pipeline notes

The short Windows commands are in README.md. This document explains what they do and how the security checks work.

## Setup and build

`py -3.12 run.py setup` uses Python's standard-library launcher at the project root. It verifies the exact vendor inventory and SHA-256 manifest, creates `.venv` if missing, updates pip using bootstrap.lock, installs requirements.lock offline with hash verification, verifies installed distributions and seeds synthetic accounts/data. Each task uses the project's interpreter through an argument list, so activation and PowerShell execution-policy changes are unnecessary. The application imports no third-party package until setup has installed it.

`py -3.12 run.py build` rebuilds the separate helper wheel into reports/helper-wheel/. Setup installs its already approved wheel from vendor/ as a declared dependency. Rebuilding validates the package source; it does not automatically approve newly generated bytes. Wheel build timestamps/metadata are not claimed to be bit-for-bit reproducible.

The supplied wheels target CPython 3.12 Windows x64 and Linux x86_64. Windows is the documented user workflow. Linux wheels remain to reproduce the earlier saved evidence and support local verification in the supplied execution environment. No Windows run has been claimed.

## Run and data

`run.py run` launches scripts/run.py in the virtual environment. That script starts API, Resource and Processor as separate uvicorn subprocesses, with separate ports and minimal environment variables, then waits until stopped. Ctrl+C stops the group. Seed data is generated automatically if missing; existing datasets are preserved. A separate `run.py seed` command is provided for explicit seeding.

Data and local service logs are written to .runtime/. Sessions become invalid on restart because signing keys are regenerated. To reset the demonstration, stop the server, remove only this project's .runtime/ folder, and run setup or seed again. No real data should be stored here.

## Tests and gates

`run.py test` runs the existing test suite and saves reports/tests.xml. `run.py check` executes scripts/ci.py, which performs ten stages: exact artifact checks, installed dependency inventory, compilation, helper build, Ruff lint, Ruff formatting, Bandit application/helper analysis, pip-audit, the tests and a smoke workflow. Any nonzero stage blocks. Generated output is in reports/; the supplied final snapshot is in evidence/final/.

Public advisory findings block regardless of severity. Advisory-service errors also block. The local workspace-csv package has no PyPI advisory entry, so its known skip is covered by source inspection, static checks and artifact validation. Unrecognized skipped public packages block. Both the approval manifest and source repository are consumer-controlled policy and must be reviewed when updated.

The unchanged vulnerable milestone is preserved at vulnerable-lab. To inspect it without running it:

```powershell
git show vulnerable-lab:workspace_app/resource.py
git diff vulnerable-lab fixed-boundaries -- workspace_app
```

To repeat the four original probes in a separate local worktree:

```powershell
git worktree add ..\workspace-vulnerable vulnerable-lab
cd ..\workspace-vulnerable
..\secure-workspace\.venv\Scripts\python.exe -m pytest -q -k 'test_v1 or test_v2 or test_v3 or test_v4'
```

These four security assertions intentionally fail at the vulnerable tag. That tag predates the new root launcher, so the existing environment's interpreter is used directly. Keep synthetic data local and keep the final checkout on its fixed branch.

## Windows Jenkins pipeline

Jenkinsfile expects a Windows agent labelled windows-python312, with Git and Python 3.12 available to its service account. It deletes the previous workspace, checks out source, runs `py -3.12 run.py setup`, then `py -3.12 run.py check`. JUnit and analysis artifacts are archived even when checks fail. No production deployment is performed.

GitHub Multibranch discovery, push/PR webhooks and repository protections are configured in the accounts rather than by the Jenkinsfile. Follow docs/github_and_submission.md. The hosted Windows Jenkins job has not been executed in the supplied environment.
